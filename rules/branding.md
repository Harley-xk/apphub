# AI 工作规则 —— 品牌化迁移范围

> 优先级仅次于 [base.md](base.md)。本规则约束品牌化迁移（fork 自底座框架 n-1 的品牌改造）与从 upstream 同步代码时的改动范围。

## 1. 核心原则：品牌化只做前端 UI 层面

品牌化迁移只针对**用户在界面上可见的 UI 层面**进行（产品名、页面标题、logo、界面文案等品牌信息）；**框架代码层面一律不做品牌化替换**，包括：

| 层面 | 示例 | 处理 |
| --- | --- | --- |
| CSS 变量前缀 | `--n1-*` 设计 token | 保留原名，不改 `--apphub-*` |
| 组件命名前缀 | `N1Table` 封装组件 | 保留原名 |
| 文件 / 目录名 | 组件目录、样式文件名 | 保留原名 |
| 代码注释 | 头部注释、行内注释中的框架称谓 | 保留原文 |
| 设计文档 | 文档中的组件 / token 称谓 | 保留原文 |

**理由**：框架层面的替换不产生用户价值，却让每一次从 upstream（n-1）同步修复都制造大量无意义冲突；品牌化的真实诉求只在用户可见的 UI 层面。

## 2. 存量一致性优先

本仓库历史迁移已将部分框架前缀替换为 `apphub`（如 `--apphub-*` token、`ApphubTable`）。对这部分存量代码：

1. **保持现状一致**：从 upstream 合并修复时，若修复涉及已品牌化的文件，冲突解决按**文件内现行前缀**对齐——同一文件混用两套前缀会导致 CSS 变量解析失败等真实缺陷
2. **不回改**：不主动把存量 `apphub` 前缀改回原名
3. **不扩大**：不在新增代码与新迁移范围中继续做框架层面的品牌化替换

## 3. 与 upstream 同步的冲突处理约定

从 upstream cherry-pick / merge 时，冲突解决遵循「**取 upstream 语义 + 保持文件内现行前缀一致**」：upstream 的修复逻辑完整落入，仅将冲突行中的 token / 组件名对齐到该文件当前使用的前缀。
