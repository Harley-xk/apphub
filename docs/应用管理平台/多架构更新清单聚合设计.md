# 多架构更新清单聚合设计（electron latest-mac.yml）

> 本文是「默认路径按架构分发」的设计依据：在单一 `latest-mac.yml` 中聚合多架构 `files` 条目，让 electron-updater 的 generic provider 无需配置即可按本机架构取包。
> 遵循 [应用与版本管理设计](应用与版本管理设计.md) §3.4 的既有约定（D24 适配端点、不做 UA 解析），是实现主张编号 B1 ~ B9 的出处。

## 1. 背景与现状

electron-updater 的 generic provider 对 macOS 固定请求 `latest-mac.yml`，URL 不含架构维度；架构信息只在 User-Agent 与客户端本机检测中。现状端点按 `(macos, universal)` 固定槽位取包，分架构发布（x64 + arm64 分别打包）的应用在默认路径下直接 404。

已交付的架构级路由（`latest-{arch}-mac.yml`）提供显式通道，但需要客户端配置 channel，不是默认行为。本设计补齐默认路径：

- electron-updater 6.8.11 源码 `out/MacUpdater.js`：
  - `filterFilesForArch(files, isArm64Mac)`——arm64 机器（含 Rosetta）优先取文件名含 `arm64` 的条目；x64 机器排除所有含 `arm64` 的条目
  - `findFile(files, "zip", ["pkg", "dmg"])`——mac 更新只下载 zip（dmg / pkg 不参与更新链路）
- 架构判定只发生在客户端（`uname -a` / `process.arch` / Rosetta 检测），与服务端无关

因此服务端只需在 `files` 中同时列出各架构的 zip 条目，客户端会自动选型。

## 2. 目标与非目标

**目标**：`latest-mac.yml` 默认路径对分架构发布的应用可用；不解析 User-Agent；对存量 universal 应用零影响；与架构级路由并存。

**非目标**：

- Windows 聚合——`NsisUpdater` 不按架构过滤 `files`（`findFile(files, "exe")` 直接取第一个），聚合有取错包风险
- Linux 聚合——electron-updater 已原生按 `process.arch` 请求 `latest-linux-{arch}.yml`，无需聚合
- 包模型改造（同一 `(platform, arch)` 槽位多文件）——超出本期范围，见 B8
- 服务端按 User-Agent 推导架构——与既有决策冲突，明确不做

## 3. 决策主张

### B1 聚合范围仅 macOS

只改 `latest-mac.yml` 的渲染。`latest.yml` / `latest-linux.yml` 与各架构级路由行为不变。

理由见 §2 非目标：Windows 的 updater 不做架构过滤，Linux 已有原生架构级 feed。

### B2 分架构优先，universal 补位

候选版本内存在分架构包（`x64` / `arm64`）时，优先输出分架构条目；`universal` 仅在某架构缺包时作为该架构的兜底：

| 版本内包组合 | `files` 输出 |
| --- | --- |
| 仅 universal | universal（与现状一致） |
| x64 + arm64 | x64、arm64 |
| x64 + universal | universal、x64（顺序见 B4） |
| arm64 + universal | universal、arm64（顺序见 B4） |
| x64 + arm64 + universal | x64、arm64（universal 不参与） |
| 仅 x64 或仅 arm64 | 该架构条目 |

### B3 候选版本判定放宽为「任一 macos 包」

`latest-mac.yml` 的候选版本从「挂有 `(macos, universal)` 包」放宽为「挂有任一 `macos` 包（x64 / arm64 / universal）」，语义仍为：通道启用、`status = published`、semver 最大。

自研协议与 tauri 的候选查询不受影响（它们本来就带明确 `arch`）。

### B4 `files` 条目构建与顺序

- 每个架构输出「主包 + blockmap（已上传时）」；同一架构的 blockmap 紧跟主包
- 分架构都在场时顺序为 `x64 → arm64`（顺序不影响客户端选型，固定顺序保证同一数据渲染稳定）
- **universal 补位时必须排在最前**：`filterFilesForArch` 在 arm64 机器上「没有 arm64 条目 → 返回全部非 arm64 条目」，若 x64 排在 universal 之前，arm64 机器会取到 x64 包（只能靠 Rosetta 运行）。universal 前置后，缺架构的机器优先拿到 universal
- 每架构只输出一条主包（当前模型一个槽位一个包，B8）

### B5 顶层兼容字段取主包的顺序

`path` / `sha512` 取 `files[0]` 对应的主包（universal 补位场景即 universal，否则 x64 / arm64），保证不识别 `files` 的旧客户端仍能取到「最兼容」的包。`version` / `releaseDate` / `releaseNotes`（含 `[force]` 标记）渲染规则不变。

### B6 无候选时返回 404 的语义不变

应用停用 / 通道停用 / 无 published 版本 / 版本下无任何 macos 包 → 404，与现状一致。

### B7 不做服务端架构判定

服务端不读 User-Agent、不看请求头，架构选择完全交给客户端 updater 的本机检测。这是 B 路线相对架构级路由（A）的核心价值：客户端零配置。

### B8 electron 应用的 macos 包必须为 zip，且架构标记与包架构一致（发布硬拦截）

electron-updater 的 mac 更新只认 zip，dmg 只能用于首次手动安装。当前一个 `(platform, arch)` 槽位只能登记一个包，因此 electron 应用登记 macos 包时须上传 **zip 产物**。

`assertFrameworkArtifacts`（发布前置校验与已发布版本补包登记共用的唯一规则）扩展两条校验：

1. `framework = electron` 且 `platform = macos` 且 `fileName` 不以 `.zip` 结尾 → 抛 `FRAMEWORK_ARTIFACT_MISSING`（003004003）
2. `framework = electron` 且 `platform = macos`：`arch = arm64` 时文件名必须含 `arm64`；`arch = x64` / `universal` 时文件名不得含 `arm64`（大小写不敏感）

第 2 条是 B2 / B4 正确性的前提——客户端架构过滤只认文件名中的 `arm64` 标记：arm64 包缺标记会被当成 x64 分给 Intel 机器；x64 / universal 包误带标记会被 Apple Silicon 机器优先选中，且 x64 机器会直接排除它。

影响：dmg-only 的 electron 应用无法发布新版本（需补传 zip，electron-builder mac 目标同时产出 zip）；存量已发布版本不受校验回溯影响。

### B9 与架构级路由并存

`latest-{arch}-mac.yml` 保持精确槽位语义（客户端显式指定 channel 时使用），默认 `latest-mac.yml` 走本设计的聚合语义。两者互不影响。

## 4. 渲染示例

分架构发布（x64 + arm64 各有 zip + blockmap）：

```yaml
version: 1.1.0
path: app-1.1.0-mac.zip          # 取 files[0]
sha512: OWRlY2FkLXg2NA==
releaseDate: '2026-10-01T08:00:00.000Z'
releaseNotes: "[force]\n修复登录闪退"
files:
  - url: https://oss…/app-1.1.0-mac.zip
    sha512: OWRlY2FkLXg2NA==
    size: 88123456
  - url: https://oss…/app-1.1.0-mac.zip.blockmap
    sha512: YmxrLXg2NA==
    size: 123456
  - url: https://oss…/app-1.1.0-arm64-mac.zip
    sha512: OWRlY2FkLWFybTY0
    size: 90543210
  - url: https://oss…/app-1.1.0-arm64-mac.zip.blockmap
    sha512: YmxrLWFybTY0
    size: 130000
```

universal 补位（x64 有包、arm64 缺包、universal 有包）：

```yaml
files:
  - url: https://oss…/app-1.1.0-universal-mac.zip   # 必须在前：arm64 机器在此取包
    sha512: …
    size: …
  - url: https://oss…/app-1.1.0-mac.zip            # x64 机器优先取 universal 亦可运行
    sha512: …
    size: …
```

## 5. 契约与兼容性影响

1. **`latest-mac.yml` 契约变更**：从「固定 universal 槽位、不回退其他架构」变为「分架构优先 + universal 补位」。既有 e2e 契约守护用例「x64 包不得被 latest-mac.yml 命中（404）」需改写为「x64 包被聚合命中（200）」
2. **存量 universal 应用零变化**：仅 universal 时渲染结果与现状一致
3. **架构级路由零变化**：`latest-{arch}-mac.yml` 精确槽位语义不变
4. **旧版 electron-updater 兼容**：`filterFilesForArch` 自 **6.8.8** 引入（已逐版本核对 6.8.0 ~ 6.8.11 的 `out/MacUpdater.js`）；低于该版本不按架构过滤，会取 `files[0]`——分架构场景下老客户端会装到 x64 包；接入文档注明「mac 分架构发布要求 electron-updater ≥ 6.8.8」

## 6. 风险与边界

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 文件名不含 `arm64` | 客户端架构过滤只认文件名，arm64 包错命名会被当成 x64 | B8 发布硬拦截（架构标记与包架构一致） |
| 旧客户端不分架构 | 取 `files[0]`，可能装错架构 | 固定顺序 + 接入文档要求 electron-updater ≥ 6.8.8 |
| universal 补位顺序错误 | arm64 机器拿到 x64 包（Rosetta） | B4 强制 universal 前置 + 单测守护 |
| dmg 登记进更新槽位 | 客户端报 `ERR_UPDATER_ZIP_FILE_NOT_FOUND` | B8 校验 / 提示 |
| blockmap 架构串位 | blockmap 文件名随主包，过滤后仍与同架构主包成对 | 条目构建按架构成对输出 |

## 7. 测试计划

**单元测试**（`package-mac-aggregate.util.spec.ts`，新增）：选包纯函数按组合表（§3 B2）逐项覆盖，重点守护 universal 补位顺序与「universal 不参与三包共存」。

**框架产物校验单测**（`package-artifacts.util.spec.ts`）：B8 两条规则的命中与豁免（非 electron / 非 macos / zip + 标记一致），以及「发布前置」与「已发布补包登记」共用规则的回归。

**后端 e2e**（`appcenter-open.e2e-spec.ts`）：
- 分架构发布应用：`latest-mac.yml` 返回 x64 + arm64 条目，含 blockmap，顶层字段取 `files[0]`
- universal 补位应用：universal 条目在前
- 纯 universal 应用：回归现状
- 修改既有「x64 不得命中 latest-mac.yml」契约用例

**浏览器 e2e**：无（后端开放接口，页面无交互变化）。

## 8. 验收标准

1. 分架构发布（x64 + arm64）的 electron 应用，默认 `latest-mac.yml` 同时含两个架构的 zip 与 blockmap 条目
2. arm64 / x64 客户端分别取到正确架构包（以 electron-updater 6.8.x 实测或单测覆盖过滤规则）
3. universal 存量应用渲染结果不变
4. 架构级路由与 B 的默认路径并存，互不影响
5. 发布校验：electron 应用的 macos 包非 zip、或架构标记与包架构不一致时被拦截（003004003），发布前置与已发布补包登记两处生效
6. `pnpm check` 全绿，文档与实现同步
