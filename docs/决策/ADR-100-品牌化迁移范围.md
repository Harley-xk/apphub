# ADR-100：品牌化迁移范围

- 状态：已接受
- 日期：2026-10-19
- 关联：[rules/branding.md](../../rules/branding.md)（行为规则，本仓库与上游均已落地）；[ADR-001](ADR-001-菜单与路由的权限承载方式.md)（同源哲学：把不可变约定收敛为单一事实源）

## 背景

本项目 fork 自 n-1 全栈底座。fork 时进行了**全量品牌化替换**，覆盖框架代码各层面：设计 token 前缀（`--n1-*` → 自有品牌前缀）、封装组件名（`N1Table` → 自有品牌组件名）、本地存储键（`APPHUB_TOKEN` / `APPHUB_TABLE_COLS`）、文档中的组件与 token 称谓等，涉及样式、组件、工具、文档多个层面。

2026-10-19 首次从 upstream 同步修复（3 个 web 修复：暗色表格文字、暗色主色回蓝、拖拽把手），所涉 4 个文件**冲突率 100%**，且逐处检查后确认：**每一处冲突的根源都是品牌化前缀差异**——这些修复在 upstream 侧本是干净落地的，冲突成本全部由 fork 时的替换决定带来。

## 决策

**品牌化迁移只做前端 UI 层面**（产品名、页面标题、logo、界面文案等用户可见的品牌信息）；**框架代码层面一律不做品牌化替换**（token 前缀、组件命名前缀、文件 / 目录名、代码注释、文档称谓），新 fork 的项目应**全部复用框架的 `--n1-` 前缀与 `N1` 组件命名**，不指定自有品牌前缀。

行为细则（替换范围表、存量三原则、同步冲突处理约定）见 [rules/branding.md](../../rules/branding.md)，本仓库与上游 n-1 仓库同步落地。

## 理由

1. **品牌化的真实诉求只在用户可见层**：用户感知到的是产品名与界面，token 前缀与组件名对用户完全不可见，替换不产生任何用户价值。
2. **替换的代价是持续性的，而非一次性**：upstream 每一个涉及样式 / 组件 / 文档的修复，同步时都要为前缀差异重复支付冲突解决成本——首次同步即出现 3 个修复 100% 冲突率的实证。
3. **混用即静默缺陷**：同一文件混用两套前缀会导致 CSS 变量解析失败等无报错缺陷，替换扩大了出错面。

## 后果（含存量特例）

1. **本仓库为规则确立前的存量**：自有品牌前缀已全量落地（token、组件名、存储键）。存量按三原则维持——**不回改**（不恢复 n1 原名）、**不扩大**（新代码不再做框架层替换）、**文件内前缀对齐**（同步冲突按现行前缀落）。
2. **存量特例——残留检查**：本仓库正常状态不应出现 `--n1-`，一旦出现即同步漏改（静默缺陷），每次 upstream 同步后需 grep 检查。此检查**仅适用于本仓库存量**；按新规则 fork 的新项目全文复用 `--n1-` 前缀，无此负担。
3. 未来从 n-1 fork 的新项目遵循新规则，upstream 同步接近零冲突（仅业务文件冲突）。
4. 教训留痕：某项目实践证明，fork 时的全量品牌化替换在后续每次同步中以 100% 冲突率偿还，是典型的「一次性决策、持续性还债」。
